PURPOSE
-------

Production is partially synchronized with the Laravel repository, but public.migrations does not exist. The deployed application expects schema elements that are absent from production.

The synchronization must therefore be explicit and reviewed. It must not replay the entire historical Laravel migration chain.

The recommended architecture is:

1. Capture a production backup or verify a recoverable Supabase backup.
2. Run read-only preflight checks.
3. Apply a reviewed, one-time, idempotent synchronization process against the actual production schema.
4. Separate schema changes, data backfill, constraints/indexes, and compatibility corrections.
5. Run read-only postflight verification.
6. Test authentication, profile, onboarding, and generation workflows.
7. Establish a reliable Laravel migration baseline after the schema is known to match.

C. SYNCHRONIZATION ARCHITECTURE DECISION
----------------------------------------

Recommended mechanism: a manually reviewed, one-time SQL synchronization script executed by the database owner/administrator, not the normal Laravel migration runner.

Reason:

- public.migrations does not exist.
- Laravel cannot know which historical migrations were already applied.
- Several historical migrations are non-idempotent.
- Some repository migrations include data backfills.
- Production already contains a partial schema.
- A normal php artisan migrate could replay historical table creation or column changes.

Do not create or use a Laravel migration that pretends the entire historical chain was applied.
Do not run php artisan migrate --force against this production database.
Do not execute the username migration blindly through Laravel's migration runner until the migration-ledger strategy is resolved.

The synchronization script should be:

- versioned outside the historical migration chain, or kept as a DBA-controlled deployment artifact;
- reviewed before execution;
- idempotent where practical;
- run during a controlled maintenance window;
- executed with the existing server-side database role only;
- followed by read-only verification;
- followed by a separately planned migration baseline.

E. USERNAME BACKFILL STRATEGY
-----------------------------

The repository username migration performs a data backfill. The production synchronization must treat this as a separate, reviewed data operation.

Required rules:

1. Do not add UNIQUE(username) before the backfill.
2. Process users in deterministic order, preferably ORDER BY id.
3. Only backfill rows where username IS NULL or username = ''.
4. Prefer the email local-part before the '@' character.
5. If the email local-part is empty, use the legacy name.
6. If both are empty or unusable, use 'user'.
7. Lowercase the candidate.
8. Remove characters outside A-Z, a-z, 0-9, dot, underscore, and dash.
9. If normalization produces an empty string, use 'user'.
10. If the candidate is already used, append _1, _2, _3, and so on.
11. Check both existing usernames and usernames generated earlier in the same run.
12. Keep assignment deterministic by processing users by id.
13. Do not overwrite a non-empty username.
14. Do not modify email, name, password, provider fields, or personal information.

The production migration must first identify whether any username column already exists. The audit found it missing, but the synchronization should remain idempotent.

Recommended implementation approach:

- Add username as nullable.
- Create a temporary staging structure or use a controlled procedural block to calculate candidates.
- Preflight all candidate collisions.
- Abort before applying the unique index if unresolved collisions exist.
- Backfill only NULL/empty usernames.
- Verify that username is unique and non-empty for all users.
- Add the unique constraint after successful backfill.

Conceptual PostgreSQL candidate expression:

lower(
    regexp_replace(
        coalesce(
            nullif(split_part(email, '@', 1), ''),
            nullif(name, ''),
            'user'
        ),
        '[^A-Za-z0-9._-]+',
        '',
        'g'
    )
)

This expression alone is not sufficient to resolve collisions. Collision resolution must be deterministic and must account for existing usernames and candidates generated earlier in the same operation.

F. USERNAME PREFLIGHT CHECKS
----------------------------

The following queries are examples for the controlled preflight. They are NOT to be executed as part of this read-only plan.

1. Confirm the current users columns:

SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'users'
ORDER BY ordinal_position;

2. Confirm whether username already exists:

SELECT COUNT(*) AS username_column_count
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'users'
  AND column_name = 'username';

3. Count existing users requiring a username:

SELECT COUNT(*) AS users_needing_username
FROM public.users
WHERE username IS NULL OR username = '';

4. Preview normalized candidates without changing data:

SELECT
    id,
    email,
    name,
    lower(
        regexp_replace(
            coalesce(
                nullif(split_part(email, '@', 1), ''),
                nullif(name, ''),
                'user'
            ),
            '[^A-Za-z0-9._-]+',
            '',
            'g'
        )
    ) AS normalized_candidate
FROM public.users
WHERE username IS NULL OR username = ''
ORDER BY id;

5. Check duplicate normalized candidates:

WITH candidates AS (
    SELECT
        lower(
            regexp_replace(
                coalesce(
                    nullif(split_part(email, '@', 1), ''),
                    nullif(name, ''),
                    'user'
                ),
                '[^A-Za-z0-9._-]+',
                '',
                'g'
            )
        ) AS candidate
    FROM public.users
    WHERE username IS NULL OR username = ''
)
SELECT candidate, COUNT(*)
FROM candidates
GROUP BY candidate
HAVING COUNT(*) > 1;

6. Check duplicate existing usernames if the column exists:

SELECT username, COUNT(*)
FROM public.users
WHERE username IS NOT NULL AND username <> ''
GROUP BY username
HAVING COUNT(*) > 1;

7. Check for values that violate the application username format:

SELECT id, username
FROM public.users
WHERE username IS NOT NULL
  AND username !~ '^[A-Za-z0-9._-]+$';

The backfill must not proceed until the operator has reviewed candidate collisions, blank fallback cases, and the number of affected rows.

G. INDEX AND CONSTRAINT OPERATIONS
----------------------------------

After the username backfill succeeds:

1. Create the username uniqueness constraint/index:

ALTER TABLE public.users
    ADD CONSTRAINT users_username_unique UNIQUE (username);

Before applying it, verify that no duplicate or empty values remain in the backfilled set.

2. Create the provider lookup index:

CREATE INDEX users_provider_name_provider_id_index
    ON public.users (provider_name, provider_id);

The exact index name should be checked against production before creation. If an equivalent index already exists under another name, do not create a duplicate.

3. The existing email unique constraint and users primary key should be retained.

No user foreign keys are required.

H. TYPE AND DEFAULT CORRECTIONS
-------------------------------

H1. businesses.content_style

Repository expectation: JSON.
Production type: character varying.

Recommended immediate action: do not change automatically.

Reason:

- Existing production values may be plain strings rather than valid JSON.
- A type conversion could fail or require a data transformation.
- Current application compatibility should be tested first.
- The field is not required to resolve the current username authentication failure.

Before correcting it, inspect value shape and application usage. If correction is later approved, use an explicit conversion plan with a safe fallback for non-JSON values. Do not use a blind ALTER COLUMN TYPE.

H2. campaigns.target_audience

Repository expectation: varchar(255).
Production type: text.

Recommended immediate action: leave as text.

Reason:

- PostgreSQL text accepts the values expected by the application.
- This is more permissive and does not block current authentication or onboarding.
- Converting to varchar(255) could fail if any existing value exceeds 255 characters.

If exact parity is required later, first measure maximum length and handle overlength data explicitly.

H3. events.country

Repository expectation: nullable with default 'PH'.
Production: nullable with no default.

Recommended immediate action: defer unless new event creation depends on the default.

Reason:

- Existing rows are not changed by adding a default.
- Application behavior should be checked to determine whether country is always supplied.
- If the default is required, the controlled operation would be:

ALTER TABLE public.events
    ALTER COLUMN country SET DEFAULT 'PH';

Do not make the column NOT NULL.

HAVING COUNT(*) > 1;

5. Verify username constraint/index:

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public'
  AND tablename = 'users'

6. Verify provider index:

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public'
  AND tablename = 'users'
  AND indexdef ILIKE '%provider_name%provider_id%';

7. Verify remaining required columns:

SELECT required.column_name
FROM (
    VALUES
        ('first_name'),
        ('middle_name'),
        ('last_name'),
        ('suffix'),
        ('mobile_number'),
        ('username')
) AS required(column_name)
LEFT JOIN information_schema.columns actual
    ON actual.table_schema = 'public'
   AND actual.table_name = 'users'
   AND actual.column_name = required.column_name
WHERE actual.column_name IS NULL;

Expected result: no rows.

8. Verify RLS remains enabled and unchanged:

SELECT relname, relrowsecurity, relforcerowsecurity
FROM pg_class
WHERE oid = 'public.users'::regclass;

SELECT schemaname, tablename, policyname, permissive, roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public'
  AND tablename = 'users';

9. Verify the migration ledger is still not being falsely claimed:

SELECT to_regclass('public.migrations') AS migrations_table;

The synchronization process must not claim that all historical migrations have run.

K. ROLLBACK AND RECOVERY PLAN
-----------------------------

Preferred recovery is database restore or point-in-time recovery, not an improvised reverse migration.

Before synchronization:

- Confirm a recoverable Supabase backup or point-in-time recovery window.
- Export schema metadata.
- Record row counts for users and businesses.
- Record the number of NULL/empty usernames after the username column exists.
- Store the candidate mapping for each affected user in a protected operator-only artifact if policy permits.
- Record existing indexes and constraints.

If the operation fails before commit:

- Roll back the transaction if the chosen DDL/data process is transactional.
- Do not continue to subsequent stages.
- Preserve the error and preflight output.

If the operation commits and a problem is discovered later:

- Prefer restoring the database or using point-in-time recovery.
- Do not drop username or personal-information columns after application traffic has begun using them.
- Do not run the migration down method casually; dropping username would destroy the new identity data.
- If only a new index is defective, remove only the reviewed index/constraint after confirming application impact and backup status.

The username backfill is logically reversible only if the original NULL/empty state and generated mapping were preserved. Therefore the mapping must be captured before or during the controlled backfill if rollback-by-data-restoration is required.

L. MIGRATION BASELINE STRATEGY
------------------------------

After synchronization and verification:

1. Treat the synchronized production schema as the baseline state.
2. Do not insert fabricated historical rows into public.migrations claiming that every old migration ran unless the exact historical state is proven.
3. Choose one controlled baseline approach with the Laravel team:

   Approach 1: Establish a new baseline migration representing the already-existing production schema, mark it as the baseline for future environments, and keep subsequent migrations after that baseline.

   Approach 2: Use a separate deployment schema-management ledger outside Laravel's migrations table, recording the reviewed synchronization version and checksum.

   Approach 3: Rebuild a faithful production clone, apply the repository migrations in a controlled environment, compare the result, and then reconcile the production baseline explicitly.

4. Document which repository migrations are represented by the existing external schema.
5. Document which synchronization operations were applied.
6. From that point forward, require every new schema change to have an auditable migration or synchronization artifact.
7. Never use local migration status as proof of production migration state.

The preferred long-term approach is a reviewed baseline plus normal forward-only Laravel migrations for all future changes.

M. RISK ASSESSMENT
------------------

High risk:

- Username backfill collisions.
- Creating UNIQUE(username) before resolving duplicates.
- Running all historical migrations without a migration ledger.
- Applying a blind type conversion to businesses.content_style.
- Losing the mapping between original users and generated usernames.
- Synchronizing while concurrent deployments write users or businesses.

Medium risk:

- Adding nullable columns during active traffic.
- Creating indexes while high-volume writes are active.
- Restoring events.country default without checking application expectations.
- Establishing a baseline that falsely claims historical migrations were applied.

Lower risk:

- Adding nullable personal-information columns.
- Adding nullable business registration/address columns.
- Leaving campaigns.target_audience as text because it is more permissive than varchar(255).
